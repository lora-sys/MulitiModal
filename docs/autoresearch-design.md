# AutoResearch 最小设计

## 为什么这样设计

一次研究需要把“想法是否有效”和“测量方式是否可信”分开。人类定义问题、数据边界和成功标准，Agent 在允许的范围内提出可检验的变化；固定评价器使用同一协议判断结果。每轮的价值不仅是一个分数，还包括提交、假设、失败原因和可复查的证据。下一轮应利用这些信息，而不是盲目抽样。

这个项目采用最小的单 Agent 闭环：基线 → 假设 → 单文件改动 → 隔离执行 → 固定评价 → 记录 → 保留或回退。每次只改一个可解释的研究假设；一次假设可以包含实现该假设所需的多个局部代码改动。按研究简报约定的指标方向、资源约束和晋级规则比较。若分数差异可能来自随机波动，应在简报约定的种子或重复评估下核实，不能把微小差异直接表述为稳定提升。

## 人类和 Agent 各负责什么

研究者提供 [研究简报](autoresearch-brief.md)：问题、产物、数据许可与划分、基线、指标和评价器、可修改范围、运行环境、预算、停止与交付条件。Agent 在这些边界内选择下一项实验，保留每次运行的代码和证据，并向研究者说明结果能支持什么、不能支持什么。锁定测试不能在候选比较中反复使用。

固定评价器必须与提案 Agent 的可写环境隔离；候选代码必须运行在 OS/容器边界中。当前 `prepare.py` 用本机 Python 子进程和临时目录执行候选，没有 OS/容器隔离，也没有阻断网络。因此 `AGENT_ISOLATION_UNVERIFIED` 仍然成立，不能据此声称真实研究评价可信。

独立环境所需的权限、结果认证与验证条件见[部署契约](trusted-evaluator.md)。

## 最小模块

| 模块 | 责任 |
| --- | --- |
| [通用 Skill](../skills/autoresearch/SKILL.md) | 按研究者冻结的协议驱动实验 |
| [候选文件](../src/research/train.py) | 研究循环允许修改的训练代码 |
| [固定协议与运行器](../src/research/prepare.py) | 读取数据和协议、运行候选、评分并记录结果 |
| [只读监控](../src/research/dashboard.py) | 展示状态、指标和结果历史 |

证候任务的固定协议在 [prepare.py](../src/research/prepare.py)，可编辑候选在 [train.py](../src/research/train.py)。任务适配必须自己定义数据与评价；Skill 不替研究者猜这些内容。

## 证据与限制

- `results.tsv` 是本地实验记录；它能防止意外混用已记录的协议，并校验候选提交，但本身不具备独立认证。可写结果文件不能证明分数由可信评价器产生。
- 默认 `strict` 晋级要求主指标严格改善；若研究简报冻结了其他晋级规则，可用 `external`，由任务评价器执行该规则并将规则及其代码纳入协议。历史记录本身不会执行外部规则，同一 run 不能混用策略。
- 合成运行标为 `SMOKE_ONLY`，只证明工程路径，不证明任何模型的外部泛化或临床有效性。即使提供真实数据参数，当前本机候选执行边界也不满足可信研究要求。
- 监控不持有运行控制权；Agent 中断后应先核对 Git HEAD、结果文件和历史，再决定下一步。当前没有持久调度器，也不保证进程中断后自动恢复。
- 可复用经验至少记录方法、证据和适用条件。单次结果是观察；独立复现后才可标为已验证；影响团队的约定由人确认。

这个设计借鉴 [Karpathy AutoResearch](https://github.com/karpathy/autoresearch) 的单文件、固定预算与逐轮决策，以及 [Hyra 2.0](https://hunyuan.tencent.com/research/hyra2) 对可复用工具与证据积累的重视。它没有实现 Hyra 的多层代理、持久队列或共享知识库；这些能力应在确有并行和长期运行需求时再增加。
